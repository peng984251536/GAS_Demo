# Buff 系统设计原则

本文是 Buff 与战斗机制的设计依据。具体例子见 `BuffSystem-Cookbook.zh-CN.md`，实现进度见 `BuffSystem-Roadmap.zh-CN.md`。

## 1. 核心原则

**Buff 只声明"角色现在处于什么状态、挂着什么规则"，机制本身由各个系统实现。**

- Buff 不直接写机制逻辑，例如不在 Buff 里写"怎么射箭"。
- 系统不判断"身上有没有某个具体 Buff"，只读取标签、属性和上下文。
- 依赖方向始终是：Buff → 标签/属性/上下文 ← 系统。两边互不认识。

## 2. 四层：一个效果从哪里介入

判断标准是"Buff 交给了角色什么东西"。

| 层 | Buff 交出的东西 | 适用情况 | 例子 | 实现方式 |
|---|---|---|---|---|
| 数值层 | 属性修改 | 只改一个到处通用的数字 | 攻击 +30%、移速 -50% | GE Modifier / Execution |
| 状态层 | 一个标签 | 角色原本就会这件事，切换到另一种**预先准备好**的做法；或者"能/不能"的开关 | 狂暴换动作集、眩晕、冻结、移动射击、反弹能力 | GE 授予标签，各系统查询标签 |
| 能力层 | 一个 GA | 角色原本**根本不会**这件事 | 获得冲刺、获得大招 | GE 授予能力，移除时自动收回 |
| 规则层 | 插入流程某一步的逻辑 | 角色还在做原来的事，但**其中某一步的结果**要变，且需要和其他 Buff 叠加组合 | 分裂箭、爆炸箭、命中冻结、命中吸血 | `UCC_BuffBehavior` + 系统钩子 |

### 判断顺序

能用上面的层解决，就不往下走：

1. 只改一个通用数字？→ 数值层
2. 角色原本会，只是换成另一套预先准备好的做法，或者是一个开关？→ 状态层
3. 角色原本不会？→ 能力层
4. 原来的事照做，只是过程中某一步要变？→ 规则层

### 状态层与规则层的关键区别

- 状态层是**切换**：两个状态同时存在时只能选一个，需要明确优先级。
- 规则层是**叠加**：多个 Buff 可以同时修改同一个环节，结果自动组合。

### 数值层与规则层的边界

- 简单数字、到处通用 → 属性。
- 只在某个具体流程里有意义（"这次放箭射几支"），或依赖情境（只在命中时、只对连招第三段），或不止一个数字 → 规则层。

## 3. 五个横向维度

四层回答"怎么生效"。设计任何 Buff 还要过一遍下面五项：

| 维度 | 要回答的问题 | 本项目中的落点 |
|---|---|---|
| 获取 | 从哪来？有什么前置条件？ | 掉落/选择系统负责，Buff 系统只提供查询 |
| 共存 | 和其他 Buff 冲突怎么办？ | 用标签做互斥组（GE 按标签移除）；状态层需要明确优先级，不能依赖添加顺序 |
| 作用对象 | 作用于自己，还是通过自己作用于别人？ | "命中时给目标施加 Debuff"是规则层串联状态层，跨两个角色 |
| 生命周期 | 按秒、按场次、按次数？何时结束？ | GE Duration；特殊计时用 Behavior 自行管理 |
| 成长 | 等级、稀有度、叠层？ | GE Level 与 StackCount；Behavior 钩子接收层数 |

## 4. 规则层的两种钩子

| 类型 | 用途 | 例子 | 实现 | 底层成本 |
|---|---|---|---|---|
| 事后反应型 | 某事发生后额外做点事 | 命中冻结、击杀回血 | 系统在关键时刻发 GameplayEvent；Behavior 或被动 GA 监听 | 每个时机一行发事件代码 |
| 事前修改型 | 某事发生前修改参数 | 射几支箭、往哪射 | 系统构造上下文结构 → 交给 Buff 修改 → 按上下文执行 | 需要把"决定"和"执行"拆开 |

### 规则

当前已接入的事前决策点：`Hook.Projectile.Fire`（`UCC_BowShoot::ReleaseArrow`）。上下文为 `FCC_ProjectileFireContext`，具体实现见 [四种 Buff](FourExamples.zh-CN.md)。其他钩子按需求后续添加。

- **钩子放在决策点**，不放在每个函数里。动作游戏通常不超过十个：开始攻击、发射投射物、命中、计算伤害、扣血后、受击、闪避、击杀、死亡。
- **不预先铺设钩子**。第一个真正需要它的 Buff 出现时再加。
- **优先用 GAS 原生能力**：能用"事件 + 被动 GA"或"属性/标签影响 Execution"解决的，不自己写钩子。
- **事前修改型钩子由 BuffComponent 遍历生效中的 Behavior 实例调用**，不用委托订阅。实例生命周期已由 `StartSpecials`/`StopSpecials` 管理，不会漏取消订阅，调用顺序确定。
- **钩子函数接收叠层数**，因为 Behavior 每个 GE 句柄一份，叠层不会重新执行 `OnApplied`。

### 系统侧的标准结构：构造 → 修改 → 展开 → 执行

```
① Build    根据配置构造"默认这一次"的上下文（不认识任何 Buff）
② Modify   交给 Buff 修改（只有这一步和 Buff 有关）
③ Resolve  把上下文展开成具体执行参数（数学计算集中在这里）
④ Execute  纯执行（不认识任何 Buff）
```

### 组合规则必须写清楚

每个上下文字段要约定多个 Buff 同时修改时的合并方式，例如：数量相加、角度取最大、倍率相乘。约定写在字段注释里。

## 5. 投射物：发射时快照

投射物携带的效果（伤害、爆炸、附加 GE）在**发射时**写入投射物自身的 Payload，命中时直接执行 Payload，不再回头查射手的 Buff。

原因：箭飞行途中 Buff 可能结束、射手可能死亡；快照让投射物成为自给自足的对象，行为确定、易于调试。

## 6. 伤害管线

- 唯一入口：`UCC_DamageStatics::ApplyDamage`。
- 伤害请求携带来源标签 `Damage.Source.*`（Melee / Projectile / DoT / Deflected …），供 Buff 过滤"我的攻击"。
- **持续伤害必须带 `Damage.Source.DoT`**，"命中触发"类 Buff 默认排除它，防止 Buff 互相触发形成死循环。
- 实际扣血之后（AttributeSet 的 `PostGameplayEffectExecute`）且最终伤害 > 0 时，发送：
  - `Event.Combat.DamageDealt` → 攻击者
  - `Event.Combat.DamageTaken` → 受击者
  - Payload：Instigator、Target、EventMagnitude（最终伤害）、InstigatorTags（来源标签）

## 7. 阵营

- 敌我关系由唯一查询 `IsHostile(A, B)` 决定；有效阵营 = 基础阵营（来自 CharacterConfig），被 `State.Charmed` 等状态临时覆盖。
- 索敌、近战判定、投射物命中、伤害施加都必须用它。
- 魅惑、召唤物、友军、反弹投射物都依赖它。

## 8. 网络

- Behavior 只在服务器执行；纯服务器逻辑（召唤、AI、伤害）可以直接放在 Behavior 里。
- 玩家能直接感受到的机制（换动作、改输入、能否移动）必须让本地客户端立即知道：用标签（随 GE 复制或预测）驱动，而不是只靠服务器 Behavior。

## 9. 生命周期检查清单

Buff 授予的所有东西（标签、GA、钩子、召唤物、计时器、对其他 Actor 的修改）必须在以下每条路径上正确收回：

- [ ] 正常到期
- [ ] 被驱散 / 主动移除
- [ ] 被抑制（`bIsInhibited`），以及从抑制恢复
- [ ] 叠层增减
- [ ] 持有者死亡
- [ ] 关卡切换 / EndPlay
- [ ] 机制在动作进行中切换时的行为已定义（打断、等当前动作结束、保持到结束）
