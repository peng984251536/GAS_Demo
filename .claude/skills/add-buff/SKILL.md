# 新增 / 修改 Buff 的流程

开始前先读 `Docs/Buff/BuffSystem.zh-CN.md`。若 Buff 与 `Docs/Buff/BuffSystem-Cookbook.zh-CN.md` 中的某个案例相似，照该案例实现。

## 第 1 步：归类（写代码之前完成）

用一段话回答下面每一项，并写进改动说明里：

1. **层**：按顺序判断，能用上层就不用下层。
   - 只改通用数字 → 数值层
   - 角色原本会，换成预先准备好的另一种做法，或者是开关 → 状态层（授予标签）
   - 角色原本不会 → 能力层（授予 GA）
   - 原来的事照做，过程中某一步的结果变了 → 规则层（Behavior + 钩子）
2. **规则层时**：事后反应型（监听事件）还是事前修改型（修改上下文）？挂在哪个决策点？
3. **作用对象**：自己，还是通过命中作用于别人？后者需要拆成"我的规则层 Buff"+"目标的状态层 Buff"两个资产。
4. **共存**：和哪些 Buff 冲突或叠加？上下文字段的合并方式（相加 / 取最大 / 相乘）是什么？
5. **生命周期**：何时结束？动作进行中切换时如何处理？
6. **网络**：玩家是否需要即时感受到？需要则必须由标签驱动，不能只靠服务器 Behavior。

## 第 2 步：检查依赖的基础设施

查 `Docs/Buff/BuffSystem-Roadmap.zh-CN.md`：

- 依赖项已具备 → 继续。
- 依赖项缺失 → **先停下**，向用户说明缺什么、建议的实现顺序，确认后再做。不要为了单个 Buff 在系统代码里写特例绕过。

## 第 3 步：实现

- 不在 `UCC_BuffDefinition` 中新增字段。
- 不在技能、AI、伤害代码中判断具体 Buff；只读标签、属性、上下文。
- 伤害一律走 `UCC_DamageStatics::ApplyDamage` 并填写 `Damage.Source.*`。
- 敌我判断一律用 `IsHostile`。
- Behavior：`OnApplied` 里创建/订阅的一切，`OnRemoved` 里清理；参数做成 `EditDefaultsOnly`，让策划可配。
- 新钩子：只在第一个需要它的 Buff 出现时添加，放在决策点，并更新设计文档第 4 节的钩子列表。
- 新的上下文字段：注释里写明合并方式。

## 第 4 步：验证

1. 运行 `Tools/HarnessChecks/check_buff_rules.sh`，不得新增报错。
2. 在 `Source/GAS_Demo/Private/Tests/` 补充自动化测试（`GAS_Demo.Buff.*`），至少覆盖：
   - 施加后效果生效
   - 移除后完全恢复（标签、GA、订阅、生成物）
   - 被抑制时失效、恢复后重新生效
   - 与一个会修改同一环节的 Buff 同时存在时，结果符合约定的合并方式
3. 对照设计文档第 9 节生命周期清单逐项确认。
4. 基础设施有变化时更新 Roadmap；新的典型案例补充到 Cookbook。
